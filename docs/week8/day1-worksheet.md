# 사전 워크시트: 누적곱을 SQL로 — LN/EXP 트릭 손풀기

> 8주차 Day 1 (Session 1-3) 사전 배포용 워크시트. 소요 30-40분. 금요일 수업 전까지 풀어 오세요.

---

## 0. 왜 이 워크시트인가

금요일 수업에서 "수정주가"를 SQL로 계산합니다. 핵심 쿼리는 강의 화면에서 보면 한 줄입니다. 하지만 그 한 줄에는 (1) 누적 곱셈이라는 낯선 연산 (2) 로그를 이용한 우회 (3) 거꾸로 흐르는 윈도우 프레임, 세 가지가 압축되어 있어서 **직접 짜 보지 않으면 수업에서 눈으로만 이해하고 손은 못 따라오게 됩니다.** 그래서 분할이 딱 한 번만 있는 5행짜리 장난감 데이터로 미리 손을 풀어 둡니다.

준비물은 BigQuery 콘솔뿐입니다. 모든 쿼리가 WITH 절 안에서 데이터를 직접 만들기 때문에 **테이블 적재가 필요 없고, 처리 바이트도 0에 가깝습니다** (그래도 실행 전에 우측 상단 처리 바이트 미리보기를 확인하는 습관은 유지하세요).

## 1. 장난감 데이터

가상 종목 "FINDA"의 5거래일 종가입니다. 6월 4일에 **5:1 액면분할**이 있었습니다 (1주가 5주가 되고, 가격 표시는 5분의 1로).

| date | close (원) | 비고 |
|---|---|---|
| 2026-06-01 (월) | 50,000 | |
| 2026-06-02 (화) | 52,000 | |
| 2026-06-03 (수) | 54,000 | 분할 전 마지막 거래일 |
| 2026-06-04 (목) | 10,900 | **5:1 분할 당일 — 이미 분할 후 가격** |
| 2026-06-05 (금) | 11,000 | |

분할 이벤트 테이블은 한 행입니다.

| date | split_ratio |
|---|---|
| 2026-06-04 | 5.0 |

그리고 수업에서 쓸 정의 두 줄을 미리 받습니다.

- **어떤 날짜 d의 수정계수 = d보다 이후에 발생한 모든 분할 비율의 곱** (이후에 분할이 없으면 1)
- **수정 종가 = 종가 / 수정계수**

## STEP 1. 손으로 계산하기 (10분)

SQL보다 먼저 손입니다. 아래 질문에 순서대로 답하며 표의 빈칸을 채우세요.

- (1) 6월 5일 이후에 분할이 있습니까? 그럼 6월 5일의 수정계수는 얼마입니까?
- (2) 6월 4일은 분할 당일입니다. 이날의 10,900원은 분할 전 단위입니까, 분할 후 단위입니까? 그렇다면 이날의 수정계수에 자기 자신의 분할 비율 5를 곱해야 합니까?
- (3) 6월 3일의 54,000원은 분할 전 단위입니다. 지금(분할 후) 단위로 읽으려면 얼마로 나눠야 합니까?
- (4) 6월 1일과 2일도 같은 논리로 채우세요.

| date | close | 수정계수 | adj_close (= close / 수정계수) |
|---|---|---|---|
| 2026-06-01 | 50,000 | | |
| 2026-06-02 | 52,000 | | |
| 2026-06-03 | 54,000 | | |
| 2026-06-04 | 10,900 | | |
| 2026-06-05 | 11,000 | | |

채우고 나면 adj_close 열이 "절벽 없이" 10,000에서 11,000 사이를 부드럽게 오가는지 확인하세요. 절벽이 남아 있다면 (2)번을 다시 생각해 보세요.

## STEP 2. SQL로 데이터를 만들고 factor 붙이기 (10분)

BigQuery 콘솔에서 아래 쿼리의 빈칸 두 개를 채워 실행하세요. 목표: 모든 행에 `factor` 컬럼을 만들되, **분할일이면 분할 비율, 아니면 1**이 되게 합니다.

```sql
WITH prices AS (
    SELECT DATE '2026-06-01' AS date, 50000 AS close UNION ALL
    SELECT DATE '2026-06-02', 52000 UNION ALL
    SELECT DATE '2026-06-03', 54000 UNION ALL
    SELECT DATE '2026-06-04', 10900 UNION ALL
    SELECT DATE '2026-06-05', 11000
),
splits AS (
    SELECT DATE '2026-06-04' AS date, 5.0 AS split_ratio
)
SELECT
    p.date,
    p.close,
    COALESCE(____________, ____) AS factor    -- (빈칸 1), (빈칸 2)
FROM prices AS p
LEFT JOIN splits AS s
    ON p.date = s.date
ORDER BY p.date;
```

- (빈칸 1) LEFT JOIN이 실패한 날(분할이 없는 날)에는 splits 쪽 컬럼이 무엇이 됩니까? 그 자리에 넣을 컬럼은 무엇입니까?
- (빈칸 2) 그 NULL을 무엇으로 바꿔야 "곱해도 아무 일도 안 일어나는" 값이 됩니까?

실행 결과에서 6월 4일 행만 factor가 5.0이고 나머지 네 행은 1.0이면 통과입니다.

## STEP 3. 누적곱을 LN과 EXP로 바꾸기 (10분)

**(1) 문제 인식.** STEP 1의 수정계수는 "이후 분할 비율의 누적 곱"입니다. 그런데 SQL 집계 함수에는 SUM(누적 합)은 있어도 PRODUCT(누적 곱)가 없습니다. 우회가 필요합니다.

**(2) 로그의 성질 확인.** 아래를 BigQuery에서 실행해 정말 6이 나오는지 확인하세요.

```sql
SELECT
    LN(2) + LN(3) AS ln_sum,          -- LN(2 x 3) = LN(2) + LN(3): 곱이 합이 된다
    EXP(LN(2) + LN(3)) AS should_be_6  -- EXP가 로그를 되돌린다
```

즉 **여러 수의 곱 = EXP(각 수의 LN의 SUM)** 입니다. 곱셈 문제를 로그 세계로 보내 SUM으로 풀고, EXP로 되돌아오는 것입니다.

**(3) 방향과 프레임.** 이제 "어떤 행들의 factor를 SUM 대상으로 삼을지"를 윈도우로 지정해야 합니다. 다음 질문에 답하세요.

- (질문 1) 수정계수는 "그 날짜보다 **이후**" 행들의 factor 곱입니다. `ORDER BY date`를 어느 방향으로 정렬해야 "이후 행들"이 윈도우의 앞쪽(PRECEDING)에 오게 됩니까? — ASC 또는 DESC 중 택일
- (질문 2) 분할 당일의 가격은 이미 분할 후 단위였습니다 (STEP 1의 (2)). 그러면 윈도우에 자기 자신 행을 포함해야 합니까? 포함하지 않으려면 프레임의 끝을 `CURRENT ROW`와 `1 PRECEDING` 중 무엇으로 잡아야 합니까?
- (질문 3) 가장 최신 날짜(6월 5일)는 자기보다 앞(더 미래)의 행이 하나도 없습니다. 빈 윈도우에 대한 SUM은 무엇을 돌려주고, 그것을 정의("이후 분할 없으면 계수 1")에 맞게 고치려면 어떤 함수로 감싸야 합니까?

## STEP 4. 완성 쿼리 실행과 대조 (5-10분)

STEP 3의 답으로 아래 빈칸 네 개를 채워 실행하세요.

```sql
WITH prices AS (
    SELECT DATE '2026-06-01' AS date, 50000 AS close UNION ALL
    SELECT DATE '2026-06-02', 52000 UNION ALL
    SELECT DATE '2026-06-03', 54000 UNION ALL
    SELECT DATE '2026-06-04', 10900 UNION ALL
    SELECT DATE '2026-06-05', 11000
),
splits AS (
    SELECT DATE '2026-06-04' AS date, 5.0 AS split_ratio
),
base AS (
    SELECT
        p.date,
        p.close,
        COALESCE(s.split_ratio, 1.0) AS factor
    FROM prices AS p
    LEFT JOIN splits AS s
        ON p.date = s.date
),
factored AS (
    SELECT
        b.date,
        b.close,
        b.factor,
        ________(                                       -- (빈칸 3) 빈 윈도우의 NULL 처리
            EXP(SUM(____(b.factor)) OVER (              -- (빈칸 4) 곱을 합으로 바꾸는 함수
                ORDER BY b.date ____                    -- (빈칸 5) 미래 -> 과거 방향
                ROWS BETWEEN UNBOUNDED PRECEDING AND ____ PRECEDING   -- (빈칸 6) 자기 자신 제외
            )),
            1.0
        ) AS adj_factor
    FROM base AS b
)
SELECT
    f.date,
    f.close,
    f.factor,
    f.adj_factor,
    ROUND(f.close / f.adj_factor, 0) AS adj_close
FROM factored AS f
ORDER BY f.date;
```

실행 결과를 STEP 1의 손 계산 표와 한 행씩 대조하세요. 체크리스트:

- (1) 6월 1일부터 3일까지 `adj_factor`가 5, 6월 4일과 5일은 1인가
- (2) `adj_close`가 손 계산과 다섯 행 모두 일치하는가
- (3) 일부러 (빈칸 6)을 `CURRENT ROW`로 바꿔 다시 실행해 보세요. 어느 날짜의 값이 어떻게 이상해집니까? 왜 그런지 STEP 1의 (2)로 설명해 보세요.
- (4) 일부러 (빈칸 3)의 함수를 지워 보세요. 어느 행이 NULL이 됩니까?

(3)번과 (4)번의 "일부러 망가뜨리기"까지 해 보면 수업에서 디버깅 시간이 크게 줄어듭니다.

## 더 생각해 보기 (선택)

- (1) 분할이 두 번(예: 6월 2일에 2:1이 하나 더) 있다면 6월 1일의 수정계수는 얼마여야 합니까? 손으로 먼저 구하고, splits CTE에 한 행을 추가해 쿼리로 확인해 보세요. (손 계산: 2 x 5 = 10)
- (2) 액면병합(5주를 1주로, split_ratio = 0.2)이라면 이 쿼리가 그대로 동작할까요? LN이 정의되는 조건과 연결해 생각해 보세요.

## 정답

### STEP 1 표

| date | close | 수정계수 | adj_close |
|---|---|---|---|
| 2026-06-01 | 50,000 | 5 | 10,000 |
| 2026-06-02 | 52,000 | 5 | 10,400 |
| 2026-06-03 | 54,000 | 5 | 10,800 |
| 2026-06-04 | 10,900 | 1 | 10,900 |
| 2026-06-05 | 11,000 | 1 | 11,000 |

- (1) 이후 분할이 없으므로 1
- (2) 분할 후 단위이므로 자기 자신의 5는 곱하지 않음 → 1
- (3) 5로 나눠 10,800

### 빈칸 정답

| 빈칸 | 정답 | 이유 |
|---|---|---|
| (빈칸 1) | `s.split_ratio` | JOIN 실패 시 NULL이 되는 splits 쪽 컬럼 |
| (빈칸 2) | `1.0` | 곱셈의 항등원 — 곱해도 값이 안 변함 |
| (빈칸 3) | `COALESCE` | 빈 윈도우의 SUM은 NULL → 정의대로 1로 대체 |
| (빈칸 4) | `LN` | 곱을 합으로 바꾸는 자연로그 |
| (빈칸 5) | `DESC` | 미래가 앞에 오게 뒤집어야 PRECEDING이 "이후"가 됨 |
| (빈칸 6) | `1` | 자기 자신(CURRENT ROW)을 빼고 바로 앞 행까지 — 분할 당일 이중 수정 방지 |

### STEP 4 (3), (4) 관찰 정답

- (3) `CURRENT ROW`로 바꾸면 6월 4일의 adj_factor가 5가 되어 adj_close가 2,180으로 무너집니다. 분할 당일 가격은 이미 분할 후 단위인데 또 5로 나눴기 때문입니다 (이중 수정).
- (4) `COALESCE`를 지우면 최신 날짜인 6월 5일 행의 adj_factor와 adj_close가 NULL이 됩니다.

### 더 생각해 보기 정답

- (1) 6월 1일의 수정계수는 10 (이후 분할 2와 5의 곱), adj_close는 5,000
- (2) 동작합니다. LN은 양수에만 정의되는데 0.2는 양수이므로 문제없습니다. 병합은 계수가 1보다 작아져 과거 가격이 오히려 커지는 방향으로 수정됩니다
